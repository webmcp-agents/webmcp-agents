To send the same traces to two backends (an LLM tool for the team that tunes prompts, and your APM for the on-call
engineer), do not add a second exporter to the chat handler: each one adds a request at the end of every turn, and its
keys live in your app. Point the app at one OpenTelemetry Collector instead, and let the Collector fan out. The keys
then live in the Collector, and you can drop or rewrite attributes before anything leaves your network.

## Try it on your machine

To see what the app sends before you pick a backend, run a Collector that only prints:

<include meta='title="otel-collector.yaml"'>/_examples/observability/otel-collector.debug.yaml</include>

<include meta='title="terminal"'>/_examples/observability/run-collector.debug.sh</include>

Set `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` in the app, send one message, and the Collector prints the
trace. This is the setup this library was verified against, over `http/json`, `http/protobuf` and `grpc`: one trace per
turn, the page's run span as the root, the server's model steps and the page's tool calls as its children.

## Troubleshooting

Set `WEB_AGENTS_OTEL_DEBUG=true` first: the layer then prints each exported span to the console, redacted.

<Accordion>
  <AccordionItem title="No span arrives, and nothing fails">
    With no `OTEL_EXPORTER_OTLP_*` variable, no `exporters`, no `spanProcessors` and no provider registered by the app,
    the layer is off, and says so once in development ([Where spans go](/observability/where-spans-go)). Check that
    `OTEL_SDK_DISABLED` is not `true` and `WEB_AGENTS_OTEL_ENABLED` is not `false`.
  </AccordionItem>
  <AccordionItem title="One error names a package">
    A protocol whose package is not installed turns that target off with one error naming it:
    `@opentelemetry/exporter-trace-otlp-proto` for `http/protobuf`, `@opentelemetry/exporter-trace-otlp-grpc` for
    `grpc`. Without the three OpenTelemetry peers, the layer is off and says which to install.
  </AccordionItem>
  <AccordionItem title="The server's spans arrive, the page's do not">
    The page posts to `/api/telemetry`. A relay that answers `404` makes the page stop sending: mount
    [the relay](/observability/relay) there. A `403` means a cross-site request or one with no `Origin`.
  </AccordionItem>
  <AccordionItem title="`403` from the backend">
    For Datadog, the intake host does not match your site. For IBM Instana, the host is usually for another region than
    your tenant's.
  </AccordionItem>
  <AccordionItem title="`404` from PostHog">
    PostHog's path does not end in `/v1/traces`: set the exact URL with `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, not the
    base variable, which appends `/v1/traces`.
  </AccordionItem>
  <AccordionItem title="`415` from Phoenix">
    Phoenix accepts protobuf only: install `@opentelemetry/exporter-trace-otlp-proto` and set
    `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`.
  </AccordionItem>
  <AccordionItem title="Every model step appears twice">
    Your app registered `@ai-sdk/otel` too and `appIntegrations` is `"keep"`, or `conventions` is `"both"`
    ([`appIntegrations`](/observability/app-integrations)).
  </AccordionItem>
</Accordion>

## Notes

<Accordion>
  <AccordionItem title="Exporter names">
    Since Collector 0.144 the OTLP exporters are `otlp_http` and `otlp_grpc`. The older `otlphttp` and `otlp` still
    work as deprecated aliases, and most vendors' docs still show them.
  </AccordionItem>
  <AccordionItem title="`endpoint` or `traces_endpoint`">
    `endpoint` is a base (`/v1/traces` is appended); `traces_endpoint` is used as given, as
    `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is in the app.
  </AccordionItem>
  <AccordionItem title="Each backend's own rules">
    The protocol, the headers and the attribute to group by are on each backend's
    [installation page](/observability/installation). `encoding: json` on an `otlp_http` exporter sends JSON; the
    default is protobuf, which every backend here accepts.
  </AccordionItem>
  <AccordionItem title="One pipeline per backend">
    When backends need different processing, give each its own `traces/<name>` pipeline with its own processors.
  </AccordionItem>
  <AccordionItem title="Batching">
    The `batch` processor is still the documented choice. Do not combine it with exporter-side `sending_queue`
    batching: the Collector warns about it.
  </AccordionItem>
</Accordion>
