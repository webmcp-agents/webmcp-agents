## Install the packages

The telemetry layer and its OpenTelemetry packages, plus the protobuf exporter: IBM's docs do not say whether OTLP JSON is accepted, so this setup sends protobuf. There is no Instana code, type or package in this library.

```package-install
npm install @webmcp-agents/telemetry @opentelemetry/api @opentelemetry/sdk-trace @ai-sdk/otel @opentelemetry/exporter-trace-otlp-proto
```

  <AccordionItem title="Identity">

  Agentless data must be tied to an entity: the `x-instana-key` header (the agent key) plus a `host.id`, `faas.id` or `device.id` resource attribute, or else the `x-instana-host` header. IBM's page is not consistent on whether `host.name` also counts. On serverless hosts set one explicitly, as both examples do.

  </AccordionItem>

  Where the protobuf package does not load, send to a Collector or to the host agent instead.

## Add the relay route

The page's spans come to your own endpoint, so the backend's key never reaches the browser. The relay refuses other origins and requests with no `Origin` (a script, not a page); the `guard` is the per-IP limit for the rest. Keep its counts in a shared store in production, as for the chat ([Limits and budgets](/security/limits)).

## Check it in IBM Instana

Start the app and send one message in the chat. Instana's GenAI views are built on OpenLLMetry and need the resource attribute `INSTANA_PLUGIN=genai`, which both examples set; they read `gen_ai.*` attributes, so keep the default `conventions: "genai"`. A `403` usually means a host for another region than your tenant's; data that is accepted but never shows up is the usual sign of a missing identity. Instana's own website monitoring (EUM) is separate and can run beside the relay.
