The run and its tool calls happen in the browser: the cursor moving, the person confirming, a call cancelled because
they scrolled away. Only the page can time those, so the page records them. `<ObserveAgents>` (or `observeAgents()`
without React) subscribes to the run events, turns each run into an `invoke_agent` span and each tool call into an
`execute_tool` span, and posts them to your [relay](/observability/relay). Render it once, next to the chat.

## Import

```ts
import { consoleExporter, observeAgents } from "@webmcp-agents/telemetry";
import type {
  BrowserSpanExporter,
  ObserveAgentsOptions,
  SpanRecord,
  StopObserving,
} from "@webmcp-agents/telemetry";
import { ObserveAgents } from "@webmcp-agents/telemetry/react";
```

`<ObserveAgents>` takes the same options as props (`ObserveAgentsProps` is `ObserveAgentsOptions`). `enabled` is read
at each run's start from the latest props, so an inline function is fine; the others are read once, when it mounts.

## Returns

- `observeAgents()` returns a `StopObserving`: call it to stop (buffered spans are sent first; no later run is
  observed). Its `flush()` sends what is buffered now and resolves once the exporters took it; it never rejects.
- `<ObserveAgents>` renders nothing. It stops, and sends what is buffered, when it unmounts.
- `consoleExporter()` takes no options and returns a `BrowserSpanExporter` whose `export(spans)` logs
  `[web-agents/telemetry] <span name>` and the span record for each span. It sends nothing.

## Notes

<Accordion>
  <AccordionItem title="What it costs the page">
    Up front, about 0.7 KB (min+gz): the subscription. The span builder, about 3.5 KB, loads when the first run the
    person agreed to starts. A page where no agent runs, or where consent is never given, never downloads it. A run's
    spans (its sub-agents' included) are sent together when the run ends, parents first, in one request; a run sends
    early once 128 spans wait or after 5 minutes. What is still buffered is sent with `keepalive` when the page is
    hidden.
  </AccordionItem>
  <AccordionItem title="A page that already runs OpenTelemetry">
    If the page registered an OpenTelemetry Web SDK provider (yours, or one from Sentry or Datadog RUM), the spans go
    to that provider instead of the relay, and join the page's own traces. The bridge to it, and
    `@opentelemetry/api`, load only on such a page. Pass `tracerProvider: "own"` to keep using the relay anyway.
  </AccordionItem>
  <AccordionItem title="While you build: print instead of send">
    `consoleExporter()` prints each span in the browser's console, redacted, and sends nothing. Any object with an
    `export(spans)` method works as an exporter; [`SpanRecord`](#spanrecord) is what
    it receives.

    **`observe.ts`**

    <include meta='title="observe.ts"'>/_examples/observability/console.ts</include>
  </AccordionItem>
  <AccordionItem title="No relay">
    A relay that answers `404` or `405` is taken as absent: nothing more is sent.
  </AccordionItem>
  <AccordionItem title="The sampled flag">
    A run this page records (consent given, kept by `sampling`) is marked at its start (`ref.sampled`,
    [`onAgentRun`](/observability/on-agent-run)), so its step requests send a `traceparent` ending in `-01` and the
    server's step spans sit under the run span. Any other run sends `-00`, and the server keeps its own tree.
  </AccordionItem>
  <AccordionItem title="Content">
    Tool inputs and results are left out unless you record them, and are redacted either way: the run events they come
    from are redacted too.
  </AccordionItem>
  <AccordionItem title="On-device runs">
    A run on the on-device model has no server. Its model steps become `chat` spans built in the browser, without
    token counts.
  </AccordionItem>
</Accordion>

:::warning[An OTLP target here puts its headers in the page]
`exporters` takes an OTLP target too, posted straight to a collector as OTLP JSON. Whatever headers it carries are in
the page: never put a key there. The relay is the default for that reason.
:::
