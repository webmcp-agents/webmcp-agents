# @webmcp-agents/core

## 0.3.0

### Minor Changes

- [#5](https://github.com/webmcp-agents/webmcp-agents/pull/5) [`2c75ea5`](https://github.com/webmcp-agents/webmcp-agents/commit/2c75ea5f62e2a18e1e74f0dce7fb39a21786df82) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - A tool's `target` function may return a promise: open the UI its control lives in (a ⌘K palette, a drawer), wait for it, return it. The call waits for it (up to `OPEN_TARGET_MS`, 3 s) before the cursor moves, so the values are typed into the opened UI.

- [#5](https://github.com/webmcp-agents/webmcp-agents/pull/5) [`7d491df`](https://github.com/webmcp-agents/webmcp-agents/commit/7d491df776898c48bf0a80203aa6ca99e539aa68) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - The cursor stays in step. Calls that overlap share one hand: the later call takes it and the earlier one finishes without a press, instead of both pressing mid-flight. A press lands on the frame that draws it, waits under way end when the person takes over, and the ring of a control pressed while the person was busy follows the page. A password is never read out (`fill` carries `"••••"`), and status is announced by the tool's title. `cursor.css`: `--agent` alone recolours the agent (the other colours derive from it), a new `--agent-edge` keeps the ring visible on dark pages, the ring no longer depends on the page's `box-sizing`, and the spotlight follows `--agent-z`. `locate` reads a name without `aria-hidden` and `hidden` parts and with an image's `alt`; a parameter's field by `name` is always a native field.

## 0.2.0

### Minor Changes

- [#1](https://github.com/webmcp-agents/webmcp-agents/pull/1) [`e02b657`](https://github.com/webmcp-agents/webmcp-agents/commit/e02b657b080039e109da16431b55374af4952624) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - Call an agent from code, and see in the devtools what the cursor will do.
  
  - chat: every agent from `defineWebAgent` has `agent.invoke(text, { adapter?, signal?, onStep? })`, which runs it on the page with no chat and resolves to `{ text, steps, messages }`. The agent stays plain data a server imports: `invoke` loads the browser loop on its first call and rejects on the server.
  - chat: `useWebAgent(agent, { adapter? })` → `{ invoke, stop, status, steps, text, error }`, with `status` "idle", "running", "waiting" (a tool parked on the person's click) or "error". `invoke` never rejects.
  - chat: `defineWebAgent({ tools })` also takes tool objects (`[tools.getCart, "list_orders"]`).
  - chat: the adapter defaults to one shared `createCloudAdapter()`: `<AgentChat agent={shopper} />` needs no `adapter` prop.
  - chat: `useAgentSession`, `useAgentChat`, `<AgentChat>`, `useWebAgent` and `agent.invoke` run one shared loop; the page's tool list is now also refreshed while the model thinks.
  - devtools: each tool shows its resolved control ("button · Add to cart", "none: runs unseen", "3 matches", "depends on the call"), the field each parameter would be typed into, its `match` and whether the current path fits, and its flags as badges. Catalog tools whose `match` does not fit are listed as "off here". Locate goes to the control the cursor would use, with no `toolname` needed. The list follows the page (URL changes and rendered controls), not only tool changes.
  - devtools: `window.agent.invoke(name, args)` is the console helper (`agent.run` stays, the same function); "Copy as" writes `agent.invoke(…)` (`toAgentInvokeCode`; `toAgentRunCode` is a deprecated alias).
  - core: `inspectTools()` lists every WebTool on the page (registered, and the catalog tools of each started `createWebAgents`) with the controls and fields the cursor would use and whether its `match` fits.

- [#1](https://github.com/webmcp-agents/webmcp-agents/pull/1) [`e02b657`](https://github.com/webmcp-agents/webmcp-agents/commit/e02b657b080039e109da16431b55374af4952624) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - `cursor.css` no longer contains Chrome's native WebMCP pseudo-classes (`:tool-form-active`, `:tool-submit-active`), so every bundler can import it, Next.js with Turbopack included: `import "@webmcp-agents/core/cursor.css"` in any framework, no copy to `public/`. - [#1](https://github.com/webmcp-agents/webmcp-agents/pull/1) [`e02b657`](https://github.com/webmcp-agents/webmcp-agents/commit/e02b657b080039e109da16431b55374af4952624) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - One way to write a tool: `execute`, plus an optional `target`. Nothing is added to the markup for the cursor.
  
  - core: a tool's control is found by role and name, like a person would: its `target` (now a locator `{ role, name, within }`, a CSS selector, or a function of the input returning either or the element), else an element marked `toolname="<id>"`, else the button, link, tab, menu item or switch named like the tool's `title` (or its id read as words). `locate` and `ToolLocator` are exported.
  - core: a tool with an `inputSchema` shows its call on the page: the cursor types each value into the control whose `name` is the parameter or whose label matches it (closest to the tool's control), before it clicks or parks. `fields` points a parameter elsewhere or turns it off; `fill(values)` runs after the typing for what cannot be typed (a custom select). Text is typed a character at a time; a number, date, range or native select is written once; a checkbox or radio is toggled by a click; a custom widget is visited, never written. Without the visuals, under reduced motion or with a yielded cursor, the values are still written, in one step. `fill` events are emitted for tools too.
  - core: the input is validated before anything moves; invalid input never reaches the page.
  - core: a `requireConfirmation` tool found by name needs exactly one matching control; with none or several the call fails with a hint instead of running unconfirmed.
  - core: flags in plain words, `readOnly`, `destructive`, `repeatable`, `external`, `safeResponse`, become the WebMCP annotations at registration (merged with `annotations`).
  - core: `tool.invoke(input)` calls a tool the way an agent would (cursor, typing, confirmation) and resolves to what `execute` returned.
  - core: `match` on a tool (a path pattern, several, or a RegExp) says where it is on. `createWebAgents({ tools, availableTools, visuals })` registers an object (or array) catalog, follows the browser's URL itself (the Navigation API, else `history`, plus back/forward and hash changes; `watchPathname` is exported) and returns `setAvailableTools`, `setTools`, `destroy`. Two tools with one id throw, naming both keys.
  - core: `registerWebTool` also takes a function returning the tool, for a definition that changes while it stays registered.
  - core: a tool that is not `readOnly` and finds no control says so once in the development console.
  - core: declarative forms: a number, date or range field is now written in one step instead of a character at a time.
  - react: `<WebAgentsProvider tools availableTools visuals>` is a thin wrapper over `createWebAgents`: `tools` is an object, `availableTools` lists tools by reference or by key, and `match` tools follow the URL with nothing wired to a router. The array catalog, `global`, `routes`, `pathname` and `context` keep working as before.
  - react: `useWebTool({ … })` takes the definition itself (or a defined tool) and returns `{ invoke, registered, supported }`. Calls read the latest render's `execute`, `target`, `fields` and `fill`.
  - react: `usePathname` follows `history.pushState` / `replaceState` in browsers without the Navigation API as well.

### Patch Changes

- [#1](https://github.com/webmcp-agents/webmcp-agents/pull/1) [`d5126c6`](https://github.com/webmcp-agents/webmcp-agents/commit/d5126c67cab8360b488dd5ba71250dab529facf1) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - - core: a `requireConfirmation` tool on a React Aria `Button` or `Link` no longer runs the element's own action after the confirming click. React Aria's `usePress` calls `el.click()` itself when the real click never reached its element; for 300 ms after the confirming click the gate now swallows that scripted click as well, on the tool's element and on one around or inside it.

- [#1](https://github.com/webmcp-agents/webmcp-agents/pull/1) [`2c38778`](https://github.com/webmcp-agents/webmcp-agents/commit/2c38778dbc9d053ce1f3ec7506246cd70946c7fb) Thanks [@mustafaskyer](https://github.com/mustafaskyer)! - - core: the cursor never presses out of sight. A control outside the viewport is scrolled to the middle and the press waits until it is there, the cursor waiting at the viewport's edge meanwhile (it used to click mid-scroll, before the control was visible; a tool that navigates left the page with nothing seen).
  - core: a control in a sticky or fixed box (a header, a drawer) that is already in view no longer scrolls the page.
  - core: after a click the cursor fades out as soon as the control it pressed is no longer under it (a drawer opened over it, the list shifted, it was removed or hidden), instead of resting on the wrong spot for `linger` ms. A control hidden mid-move no longer sends the cursor to the page's corner.
  - core: a `requireConfirmation` call always shows where to confirm. The cursor returns to the parked control once the person goes quiet (scrolling to one they were never shown), waits at the viewport's edge with the prompt when the control is out of view, and moves to the control the tool's `target` resolves to when that changes while it waits. The call fails with `unavailable`, instead of waiting for ever, when CSS hides its only control.
  - core: a `requireConfirmation` call no longer waits for ever. After 10 s without the person's click it fails with `needs_user`. A call the person starts themself (one that begins within a second of their click elsewhere: a button or chip that runs a tool, the devtools) cancels a waiting confirmation, which answers `cancelled`.
  - core: an agent's own call made while a `requireConfirmation` call waits no longer takes the "click to confirm" prompt along to its own control, and the cursor returns to the waiting control (prompt and ring) when that call is done. It used to stay where the other call left it, with nothing pointing at the confirmation.
  - core: a control pressed while the cursor had yielded gets the ring for a moment.
  - core: calls never wait on frames that are not drawn: a background tab runs them at once, and a move no frame finished lands by timer.
  - core: a press no longer releases the cursor from a newer call's move that began within its 70 ms, and the cursor's nodes are put back when a router swaps the whole `<body>`.
  - core: moving the pointer no longer makes the cursor yield; a click, a scroll, a touch or a key still does. Someone who started a call and moved the mouse off the button used to see no cursor at all. `yieldToUser: { moveThreshold: 6 }` brings the old behaviour back.
  
  Bundle budgets raised to 10 KB (visuals) and 17.5 KB (whole package).
